# FrEmulator evaluation (time-boxed)

Subject: `Java/Emulator` from [simeonpilgrim/nikon-firmware-tools](https://github.com/simeonpilgrim/nikon-firmware-tools), a whole-system emulator for Nikon Expeed (FR80 main core + TX19 sub core).

Question: can it run K-5 IIs FR80 code directly, replacing or complementing the Ghidra P-code emulation currently used (`tools/emulate_parse.py`)?

Conclusion: **yes**, for pure computation.
- `ScriptMode_parse_command` on FrEmulator gives results identical, command by command, to the Ghidra P-code emulation.
- It is much faster and needs neither Ghidra nor GhidraMCP.
- It suits batch "given this input, run one pure function" checks. Booting the whole system would need peripheral models and is out of scope.

## 1. Build

- The repository is cloned to `tools/nikon-firmware-tools/` (git-ignored).
- There is no Ant here, so `tools/fremu/build.sh` compiles with plain `javac`: JDK 25, `-source 8 -target 8`, 349 source files, about 7 seconds.
- The only obstacle: `com.nikonhacker.ApplicationInfo` is normally generated by Ant from `src/template/`; the script uses `sed` instead.
- All dependencies are in the repository's `lib/`; no network needed.

## 2. Test harness

`tools/fremu/K5ParseHarness.java` uses the same calling convention as `emulate_parse.py`:

- The image `fw/fwdc218b_dec.bin` is loaded at `0x10000000`.
- 16 MiB of RAM is mapped from `0xC0000000`.
- Registers: R4 = object, R5 = command string, R6 = the 0x30-byte `cmd[]` (`cmd[0x25]` preset to 0xFF), RP = sentinel `0x10ABFFF0`.
- It calls `FrEmulator.onClockTick()` in a loop and stops when PC reaches the sentinel, without MasterClock or peripherals.

```bash
tools/fremu/build.sh "DEBUG_MODE EN" "REGION_CODE 3"
```

## 3. Results

| Item | Ghidra P-code (`emulate_parse.py`) | FrEmulator (`K5ParseHarness`) |
| --- | --- | --- |
| 60 commands (56 positive + 4 negative) | `notes/emulate_parse_all.txt` | `notes/fremulator_parse_all.txt` |
| Return values and `cmd[]` slots | — | **60/60 identical** |
| Total time | GhidraMCP server start-up (minutes), then seconds per batch | 0.93 s including JVM start-up |
| Dependencies | Ghidra project + MCP server + inline scripts allowed | JDK only |

Each command executes between 132 and about 1300 instructions.

Instruction coverage:
- The repository's disassembler `Dfr` disassembled the script-mode code region `0x10600000–0x10620000` (128 KB, about 53 000 instructions) without any unknown opcode.
- The code uses FR80 instructions such as `LDI:20`, `ENTER/LEAVE`, `STM1/LDM1`, `DIV0S..DIV4S` and `BANDL/BORH/BTSTH`.
- The K-5 IIs main core is FR80-family like the Nikon Expeed, so the instruction sets are compatible.

## 4. Limitations

- Peripherals: the emulator's IO listeners (`Expeed4006IoListener` and others) model Nikon's register layout, which does not match Pentax/Milbeaut peripheral addresses. Any code touching `0xFFFxxxxx` IO, interrupts or timers needs new models.
- System services: RTOS calls (the `INT #0x40` kind) are handled with Nikon's conventions in FrEmulator; not verified for the K-5 IIs.
- So for now it only suits pure computation or pure-memory functions: command parsing, the `SYSPARAM.TXT` parser (`FUN_104A5ED2`), checksums, decoding and so on.

## 5. Could it emulate the AUTORUN interpreter?

`AutoTest_load_autorun` (`0x1060940E`) only reads the file:
1. gets the size (limit 20000 bytes),
2. allocates a buffer and reads the file with `Autorun_read`,
3. hands the buffer to four methods of the interpreter object (`param_1+0x60`):

| Address | Probable role |
| --- | --- |
| `0x1060A3E2` | Set source buffer and length |
| `0x1060A3EC` | Pre-process / scan (calls `FUN_10609C18`) |
| `0x1060A48C` | Build label tables and similar |
| `0x1060A75A` | Execute from line 0 |

These methods only touch the in-memory source buffer, so the file read can be skipped: put the script text into emulated memory and call the four methods in order.

- **Parsing and control flow** (`GOTO/GOSUB/IF/WHILE`, variables) are pure computation and worth running on FrEmulator.
- **Hardware-touching commands** (`PRINT` to the screen, `FILEOUT`/`FSEARCH` on the file system, `TIMERON` timers, capture commands) need breakpoints at their `CALL` targets that return stub values. This is the same technique `K5ParseHarness` uses with the RP sentinel.
- Prerequisite: reverse engineer the interpreter object's constructor and field layout; the four methods are not yet functions in Ghidra.

Conclusion: worth doing, but a separate next task outside this time box.

## 6. Recommendations

1. Prefer FrEmulator for future batch checks of pure functions, keeping Ghidra P-code as a cross-check.
2. Port the `SYSPARAM.TXT` parser `FUN_104A5ED2` next: feed it file contents and read the object fields directly to verify the keys and offsets in [sd-file-entrypoints.md](sd-file-entrypoints.md).
3. To run the boot flow one day, borrow its `Platform` / `IoListener` structure and write minimal stubs for the K-5 IIs IO addresses. This is a lot of work and needs its own assessment.
