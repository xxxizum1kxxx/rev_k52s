# 固件完整性校验（K-5 IIs 1.07 / K-5 1.16）

结论：

1. **机型标记**：升级器会检查，确定。
2. **字和为 0**：映像本身满足，但在主固件里没有找到执行这项检查的代码。
3. `tools/pentax_fw.py checksum` / `fix` 同时覆盖这两项。修改任何字节后用 `fix` 恢复字和，比让映像保持"不平衡"更安全。

本文只用于离线工具。按计划约定，**不刷入任何修改过的固件**。

## 1. 机型标记（升级器检查）

每个标记是 8 字节：`model * 0x10001`、`0xA55A5AA5`。K-5 IIs 的机型码 541（0x21D）对应 `021D021D A55A5AA5`，K-5 是 505（0x1F9）。

检查函数 `FUN_104B4EAE(obj, section)`：

- 先比较 `0x107817E0[section]` 处的机型码字和 `obj+0x280`（`FUN_104B3A54` 从固件头取机型码，或用 `obj+0x288` 覆盖）；
- 再逐个检查 `0x107817F8 + section*0x14` 表里的 5 个位置。表中存的是半字索引，乘 2 得字节偏移，相对解码后的映像缓冲区 `_DAT_C0004564`。

| section | 机型码字 | 标记偏移（去重后） |
| --- | --- | --- |
| 0 主程序 | `0x000010` | `0x1F8`、`0xFFFF0`、`0x7FFFF8`、`0x800008`、`0x9FFFF8` |
| 1 第二段 | `0xA00060` | `0xA00070`、`0xA77FF8`、`0xA7FBF0` |
| 4 副处理器 | `0xA80110` | `0xA80100`、`0xABFFF0` |

引导区的恢复升级程序 `FUN_100F0CA4` 用自己的表 `0x100F23F0` 和 `FUN_100F0D6C` 做同样的主程序标记检查。

K-5 1.16 的标记偏移和 K-5 IIs 完全相同（只是没有副处理器段），见 `k5-vs-k5iis.zh-CN.md`。

## 2. 用户升级流程（`FWDC218B.BIN`）

`FUN_104B437A`：

1. `FUN_104B6BAC` 找文件，`fwup_load_image(5, buf)` 读入；
2. `FUN_104B4FE0(obj, 5)` → `FUN_101F72BC` 依次解密 section 0、1、4（与 `pentax_fw.py` 同一 XOR 算法，IV 偏移表 `0x106F200C`，起点表 `0x106F1FF4`，字数表 `0x106F2024`，初始块号表 `0x106F203C`）；
3. `FUN_104B4EAE` 检查 0、1、4 三段的机型标记，失败报 `FUN_101F705C`；
4. `FUN_104B4F3E` 显示新旧版本，`FUN_101F7280` **禁止降级**：主程序要求当前版本 ≤ 文件版本（比较时屏蔽次字节），第二段和副处理器段总是通过；
5. `FUN_104B5120` 等写入。第二段通过 `obj+0x248` 接口送往另一颗芯片，写完由 `FUN_104B5022`（第二段）和 `FUN_104B506E`（副处理器段）把回读数据与缓冲区逐字比较，跳过字索引 `0x1E000..0x1EFFF`；
6. 主程序由 RAM 中的 `SUB_C000146C` 刷写。

这条路径上**没有求和循环**。全映像搜索 `LDI:32` 装载 `0xA00000`、`0x280000` 等长度常量也没有命中。字和如果被检查，可能在本 dump 之外的启动 ROM、RAM 刷写例程或副处理器里。

## 3. 字和为 0（映像本身满足）

| 段 | 范围（解码后偏移） | 大端 32 位字和 | 补偿字 |
| --- | --- | --- | --- |
| 主程序 | `[0x000000, 0xA00000)`，含明文头 | 0（K-5 IIs 1.07、K-5 1.16 都是） | 原厂位置未知；`fix` 默认用 `0x9FFFEC`，它在 `0x9E5F40..0x9FFFF0` 的 0xFF 填充区末尾、尾部标记之前 |
| 副处理器 | `[0xA80000, 0xAC0000)`，含 IV 所在的 `0xABFF80` | 0 | 最后一个字 `0xABFFFC` = `0x0764C0A8` |
| 第二段 | `[0xA00000, 0xA80000)` | 非 0；在前 0x800 字节的任意起点上做大端/小端前缀和搜索，都找不到和为 0 的区间 | 未知（内容像是另一层编码，留给接收芯片校验） |

这与 K-30 的 PentaxFirmwareTool 一致：K-30 也是"机型标记 + 大端 32 位字和为 0"。K-30 工具通过截短一个不用的字符串腾出 4 字节放补偿值；本工具改用填充区，不需要动字符串。K-30 文档里提到"覆盖字为 `0xFFFFFFFF` 时跳过检查"，在 K-5 IIs 上没有找到对应代码，不要依赖。

## 4. 工具用法

```bash
python3 tools/pentax_fw.py checksum fw/fwdc218b.bin          # 编码或解码的映像都可以
python3 tools/pentax_fw.py fix IN OUT                        # 默认修主程序段，补偿字 0x9FFFEC
python3 tools/pentax_fw.py fix IN OUT --section sub          # 副处理器段，补偿字 0xABFFFC
python3 tools/pentax_fw.py fix IN OUT --at 0x9FFFE8          # 指定补偿字位置
```

`fix` 的输出保持输入的编码形式（编码进、编码出）；补偿字必须在该段内、按 4 字节对齐，并且不能和任何机型标记重叠。

| 原厂完整解码 `fwdc218b_full_dec.bin` | 同上 |
| K-5 1.16 `fwdc209b.bin`（0xA80000 容器） | 两段标记正确（机型 505），主程序字和为 0 |
